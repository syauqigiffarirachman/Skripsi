# Logbook Skripsi, 14 November 2026

## Kegiatan hari ini
Fokus ke board logger. Identifikasi bangku, perubahan board logger ke STM32F030C8T6, dan tahap L1 logger dibangun dari base lalu LULUS di board.

## Identifikasi bangku (diverifikasi lewat OpenOCD, baca saja)
- ST-Link `$` -> HOST F103 (Cortex-M3, IDCODE 0x410), CDC COM12. Serial USB COM12 cocok dengan UID chip (UID0+UID2 = 0x4F344C59).
- ST-Link `X` -> LOGGER, kini **STM32F030C8T6** (Cortex-M0 r0p0, DBGMCU_IDCODE 0x...440 di 0x40015800, RAM 8 KB). SWD pulih (kegagalan 13 Nov hilang setelah kabel dipasang ulang).
- Attacker -> F030C8 terpisah, dicatu USB-B bawaan. Bukti terpisah dari `X`: chip `X` di-halt lewat SWD, konsol attacker (perintah `s`) tetap menjawab tanpa putus.
- Logger: USB-TTL CH340 (COM17) untuk daya + serial USART2 PA2/PA3; ST-Link `X` hanya data SWD.

## Keputusan desain: logger pindah ke F030C8 (SEMENTARA: tinggal board F030 yang tersedia; STM32F103C8T6 dipesan 14 Nov)
Menyimpang dari paper v3 Tabel 3.3 (Blue Pill F103). Konsekuensi yang harus masuk revisi paper/Bab 3.4:
| Aspek | Paper v3 (F103) | Logger F030C8 |
|---|---|---|
| SYSCLK | 72 MHz (HSE x9) | 48 MHz (HSE 8 MHz x6) |
| Keluaran ke PC | USB CDC | USART2 PA2/PA3 -> CH340, 115200 |

Pembagian UART: USART2 -> PC (CSV), USART1 PA9/PA10 -> host, I2C1 PB6/PB7 -> INA226 (sama pola dengan attacker). Kode F103 tetap utuh di `src/logger/` (env `logger`), diberi peringatan jangan diupload ke board F030.

## L1 logger F030 (env `logger_f030`, `src/logger_f030/main.cpp`) - LULUS di board
Fungsi satu: logger hidup dengan jam kristal yang benar. `SystemClock_Config` sendiri; kristal DIUKUR dulu (TIM14 menangkap HSE/32 lewat TIM14_OR terhadap HSI nominal 8 MHz), PLL x6 hanya bila 7-9 MHz, selain itu fallback HSI 48 MHz (`g_clk_hse`=0, `g_clk_why`). `cycles()` dari SysTick pengganti DWT. Perintah `I` di USART2. LED PC13 (`-DLOGGER_LED_PIN=PC13`).
Build: Flash 15.720 B (24,0%), RAM 1.400 B (17,1%).

Hasil di board (baca RAM lewat SWD + perintah `I` lewat COM17):
- `g_clk_hse`=1, `g_clk_why`=0, `g_sysclk_hz`=`g_pclk1_hz`=48.000.000, `g_build_id`=0x4C463031.
- Kristal terukur 8.033.341 Hz (nominal terhadap HSI 8 MHz, jadi selisih 0,4% terutama galat HSI; hanya untuk memastikan "sekitar 8 MHz", bukan akurasi kristal).
- Serial CH340 -> PA2/PA3 benar (perintah `I` dijawab), UID 2034303043335715004D0043, flash 64 KB, `beat` naik 1 per 500 ms.
- Perbandingan jam logger vs jam PC selama 60,07 s: `t_ms` +41 ppm, `cycles` +46 ppm (48,002196 MHz). Batas resolusi tes ini sekitar +-50 ppm (latensi serial ~ms, jam PC sendiri berkristal), jadi hanya menunjukkan jam logger konsisten dengan acuan kristal; BUKAN pengukuran galat kristal yang presisi.

## Temuan teknis
1. `[env]` global platformio.ini menurunkan flag USB CDC (`-DUSBCON` dst) ke env turunan; untuk F030 `build_flags` dan `monitor_port` WAJIB ditimpa (sama jebakannya dengan attacker). Tanpa itu build gagal di USBDevice.
2. `upload_protocol = custom` memberi `$SOURCE` = `firmware.bin` (bukan .elf): perintah OpenOCD `program` butuh alamat `0x08000000`. Tanpa itu "no flash bank found for address 0x0" dan verify gagal. Diperbaiki di env `logger_f030` dan `logger`.
3. LED tidak dipakai HAL tick; DWT tidak ada di M0, jadi semua profil siklus (ISR) di logger memakai `cycles()` (resolusi 1 siklus, tapi ~89 s wrap).

## L2 logger F030: INA226 - KOMUNIKASI LULUS, PENGUKURAN ARUS BELUM DIVERIFIKASI
Fungsi satu: INA226 terbaca di I2C1 (SCL PB6, SDA PB7, 400 kHz). `ina_init` menulis cfg 0x4127 (AVG 1, konversi 1,1 ms, kontinu shunt+bus) dan cal 0x0800, lalu membaca balik. Shunt R100 = 0,100 Ohm -> Current_LSB = 25 uA (CAL = 0,00512 / (25e-6 x 0,1) = 2048), sama dengan resolusi register shunt (2,5 uV / 0,1 Ohm); jangkauan arus +-819 mA. Perintah serial: `N` (init ulang + satu pembacaan), `S` (pindai I2C). Build: Flash 28.512 B (43,5%), RAM 1.716 B (20,9%), bersih (build id 0x4C463032).

Hasil di board:
- Pindai I2C: tepat satu perangkat, alamat **0x44** (bukan 0x40 seperti paper v3 dan rencana awal). Pada INA226 itu berarti A1 ke VS, A0 ke GND. Alamat di kode diubah ke 0x44; paper/Tabel 3.3 perlu dikoreksi (atau pengkabelan A1 dipindah ke GND bila ingin 0x40).
- ID pabrikan 0x5449 ("TI"), ID die 0x2260, cfg terbaca balik 0x4127, cal terbaca balik 0x0800, `g_ina_ok`=1, `g_i2c_err`=0.
- Satu pembacaan mentah: shunt raw -3 (-7,5 uV), bus raw 0 (0 mV), daya 0, arus raw -3 (-75 uA). Bus 0 mV berarti pin VBUS INA226 belum tersambung ke rail berdaya (atau mengambang), dan shunt -3 LSB hanyalah offset/noise tanpa beban. Jadi **akurasi pengukuran arus/tegangan BELUM diuji**; yang terbukti baru jalur I2C, ID chip, dan konfigurasi/kalibrasi register.
- Catatan: "arus dari shunt" tercetak -70 uA vs -75 uA dari register arus karena pemotongan bilangan bulat (-7,5 uV dicetak -7); bukan selisih fisik.

Temuan: perintah `S` dan `s`/`N`/`n` tidak peka huruf besar-kecil; paper v3 menyebut alamat 0x40, perangkat nyata 0x44.

Belum dikerjakan (lanjutan): pasang INA226 seri dengan beban (IN+/IN- di jalur 3V3 host, VBUS ke sisi beban) lalu verifikasi pembacaan dengan multimeter sebelum L3 (cuplik kontinu); L4 input-capture, L5 UART1, L6 CSV.

## Status perangkat keras logger (konfirmasi 14 Nov)
STM32F103C8T6 dipesan 14 Nov; F030C8 hanya logger sementara untuk pengembangan L2-L6. Kekurangan F030 terhadap F103 untuk peran logger: tanpa USB (CSV lewat UART, perlu baud tinggi: 115200 = ~11,5 KB/s), RAM 8 KB vs 20 KB, tanpa timer 32-bit TIM2 (capture 16-bit overflow tiap 1,37 ms di 48 MHz, perlu pencacah overflow), tanpa DWT. Resolusi tik 48 MHz setara host. Keputusan: data final N=30 diambil dengan logger F103 sesuai paper; kode logger dipisah antara bagian bergantung perangkat keras (jam, capture, jalur keluar) dan logika bersama (driver INA226, protokol, CSV) supaya perpindahan murah.

## Refaktor + L3 logger F030: cuplik INA226 kontinu + cap waktu - LULUS di board
Struktur baru supaya bisa dipakai ulang di F103: `src/logger_common/` berisi bagian BEBAS chip: `ina226.{h,cpp}` (driver kelas `INA226`, hanya Arduino Wire) dan `l3_capture.{h,cpp}` (logika cuplik; hanya butuh `plat_cycles()` dan `plat_hz()` dari platform). `src/logger_f030/main.cpp` tinggal bagian bergantung F030 (jam, pencacah siklus SysTick, USART2, peta pin). Env `logger_f030` memakai `+<logger_common/>`. Di F103 nanti `plat_cycles()` = DWT->CYCCNT, `plat_hz()` = 72 MHz.

L3 (perintah `C`, rekam 5 s, statistik berjalan tanpa menyimpan semua cuplikan): polling register MASK (CVRF), tiap konversi baru -> baca shunt+bus, cap waktu = awal pembacaan MASK yang menemukan flag. Ketidakpastian cap waktu = satu periode polling (karena tidak memakai pin ALERT). Build: Flash 31.268 B (47,7%), RAM 1.912 B (23,3%), bersih.

Hasil di board (INA226 belum diseri dengan beban, jadi yang diuji adalah PEWAKTUAN, bukan nilai arus):
- n=2479 cuplikan dalam 5000 ms, polls=24519, i2c_err=0, terlambat(>1,5x)=0, terlewat(perkiraan)=0.
- Selang cuplik: min 1863,5 us, rata2 2017,1 us, maks 2039,6 us -> **495,73 cuplikan/s**.
- Periode polling rata2 203 us (satu transaksi status + baca shunt/bus bila siap), jadi ketidakpastian cap waktu per cuplikan sekitar 0,2 ms terhadap selang 2,0 ms.
- Nilai: shunt raw -5..-1 (rata2 -3, noise/offset), bus raw 0..4 (<= 5 mV): VBUS belum tersambung ke rail, jadi tidak ada informasi akurasi arus/tegangan.
- **Temuan:** laju nyata 495,7/s, bukan ~454/s (=1/2,2 ms) yang diturunkan dari konversi nominal 1,1 ms + 1,1 ms; selang 2,017 ms diukur terhadap jam kristal logger, jadi INA226 (modul ini) berkonversi sekitar 8% lebih cepat dari nominal (toleransi osilator internal atau chip tiruan). Paper menulis "sekitar 450 cuplikan/detik": itu perlu dikoreksi menjadi ~496/s untuk modul ini, dan integrasi trapesium WAJIB memakai cap waktu nyata (bukan selang nominal). Belum diuji seberapa stabil selang ini terhadap suhu/waktu.

Bug ditemukan dan diperbaiki saat L3: percobaan pertama `cycles()` (SysTick + deteksi rollover lewat COUNTFLAG) membuat `plat_cycles()` sempat mundur sehingga rekam berakhir seketika (n=0, elapsed = 2^32 siklus = 89,5 s). Diganti pola baca-ulang (baca tik ms, VAL, tik ms lagi sampai sama), tanpa COUNTFLAG. Uji monotonik baru di perintah `I`: 300000 panggilan beruntun -> mundur=0. Dugaan penyebab (COUNTFLAG dihapus pembaca lain seperti `micros()` core) TIDAK dibuktikan; yang terbukti hanya bahwa versi baru monoton dan versi lama tidak.

Catatan batas: `cycles()` versi baru hanya aman dari thread mode / ISR berprioritas di bawah SysTick. L4 (input-capture) memakai timer hardware, jadi tidak bergantung ini.

Belum dikerjakan: verifikasi akurasi arus/tegangan INA226 terhadap multimeter (butuh INA226 diseri dengan beban, VBUS ke sisi beban, GND bersama); L4 input-capture PB1 (tunggu F103, TIM2 32-bit); L5 UART1 ke host; L6 CSV + skrip PC. Opsi perbaikan cap waktu: pakai pin ALERT (mode conversion-ready) + interrupt, butuh satu kabel tambahan.

## Logger diganti ke Blue Pill STM32F103C8T6 (board pesanan tiba 14 Nov) - L1 F103 di-flash
Bangku: ST-Link `X` -> logger F103 baru (flash kosong sebelumnya), ST-Link `$` -> host (tidak berubah), attacker sekarang lewat USB-TTL CH340 (COM17, menjawab `mode=A berjalan=ya`). CH340 COM14 lain diam (belum jelas fungsinya).
Catatan chip logger: Cortex-M3 **r2p0** (host r1p1), DBGMCU_IDCODE 0x20030410 (dev 0x410), UID terbaca nol semua (chip ST asli punya UID unik), flash size 0x80 = 128 KiB. Dugaan: klon Blue Pill (GD32F103 atau sejenis); belum terbukti, tapi perlu dicatat kalau suatu saat jam/USB/flash berperilaku beda.
Flash L1 F103 (`pio run -e logger -t upload`, serial `X` terkunci, alamat 0x08000000): programming + verify OK. Build: Flash 28.320 B (43,2%), RAM 4.540 B (22,2%).
Verifikasi lewat SWD (USB belum terpasang ke PC, jadi perintah `I` dan CDC BELUM diuji):
- `g_build_id` = 0x4C4F4731 ('LOG1'), `g_clk_hse` = 1.
- `g_sysclk_hz` = 72.000.000, `g_pclk1_hz` = 36.000.000, `g_pclk2_hz` = 72.000.000.
- RCC_CR = 0x03038183: HSE aktif dan siap (bit 16/17), PLL aktif dan siap (bit 24/25).
- `g_beat` 8 -> 12 dalam ~2,1 s (500 ms per hitung, benar).
- DWT_CTRL = 0x40000001 (CYCCNTENA = 1); CYCCNT bertambah 72,41 juta dalam sleep OpenOCD 1000 ms (waktu SWD tidak presisi, tapi sesuai 72 MHz).
BELUM diuji: USB CDC (micro-USB Blue Pill belum dipasang ke PC) dan LED PC13 (belum dikonfirmasi berkedip). Kode L2/L3 belum dipindah ke F103.

### L1 F103: USB CDC logger BELUM muncul di Windows (diagnosis, belum selesai)
LED PC13 berkedip (dikonfirmasi user, jadi firmware hidup). Micro-USB logger sudah dipasang, tetapi tidak ada COM baru: hanya COM12 (host) dan CH340. Tidak ada perangkat "Unknown/VID_0000" juga; satu-satunya entri 0483:5740 lain adalah COM3 lama (tidak hadir).
Bukti dari register logger lewat SWD (USB bukan tidak aktif):
- RCC_APB1ENR bit 23 (USBEN) = 1; `g_beat` naik.
- USB `DADDR` = 0x86: host MEMBERI alamat 6 (SET_ADDRESS sukses), terbukti juga setelah reset baru + D+ ditarik rendah lewat SWD (simulasi cabut-pasang). `FNR` = 0x853f (ada frame SOF dari host). Setelah itu `CNTR` FSUSP=1 (suspend, host berhenti mengirim SOF).
- Jadi enumerasi tahap alamat berhasil, tetapi Windows tidak pernah membuat perangkatnya; bus lalu suspend. Penyebab belum ditentukan (kandidat: kabel/port, USB-nya terhubung ke host lain, atau klon gagal menjawab permintaan deskriptor). Log PnP Windows tidak bisa dibaca tanpa admin.

### L1 F103: USB CDC logger - jalur IN (logger -> PC) BERFUNGSI, jalur OUT (PC -> logger) GAGAL
Penyebab COM tidak muncul DITEMUKAN dan diperbaiki: UID chip logger nol semua, sedangkan core (`libraries/USBDevice/src/usbd_desc.c`, `Get_SerialNum`) hanya mengisi string nomor seri USB bila UID0+UID2 != 0. Akibatnya deskriptor seri berisi 24 byte NUL, Windows menolak enumerasi (host memberi alamat lewat SET_ADDRESS lalu gagal; `DADDR` != 0 tanpa COM). Ganti kabel TIDAK mengubah hasil (alamat host berubah 6 -> 3, gagal sama). Perbaikan di `src/logger/main.cpp`: `usb_serial_fix()` mengisi `USBD_StringSerial` dengan "LOGGER000001" bila UID nol, dipanggil sebelum `ser.begin()`. Hasil: muncul **COM18**, `USB\VID_0483&PID_5740\LOGGER000001`. (Berlaku untuk SEMUA firmware yang berjalan di chip ini, mis. env lain yang memakai USB CDC.)
Jalur IN: loop menambah detak 1 Hz `LOG1 beat=N t_ms=T` ke USB (hanya bila DTR). Diterima di COM18, `t_ms` 10010, 11010, 12010, ... (selang tepat 1000 ms).
Jalur OUT: setiap `write` dari PC ke COM18 -> `SerialTimeoutException` (write_timeout 2 s), pada semua variasi DTR/RTS dan baud 9600/115200, juga dari kondisi bersih (re-enumerasi via D+ ditarik rendah lewat SWD). Kontrol: skrip yang sama menulis ke COM12 (host) berhasil, jadi bukan masalah PC/skrip. Register USB logger: EP1 = bulk OUT STAT_RX VALID, EP2 = bulk IN, EP3 = interrupt IN (konfigurasi lengkap, perangkat sudah di-configure host); tetapi EP0 STAT_RX = NAK saat idle (seharusnya VALID untuk menerima SETUP/data stage berikutnya). Dugaan (BELUM terbukti): data stage OUT pada EP0 (mis. SET_LINE_CODING) macet pada klon ini, sehingga usbser memblokir penulisan.
Konsekuensi desain: logger terutama MENGIRIM (CSV) ke PC, jadi jalur IN cukup untuk keluaran; perintah dari PC ke logger belum bisa lewat USB, gunakan sementara pemicu otomatis atau UART (USART2 PA2/PA3).
Belum dicoba: menguji apakah klon lain/firmware USB lain menerima OUT; mengganti jam logger ke 48 MHz HSI untuk mengisolasi pengaruh jam.

## L2 + L3 di logger F103 (port dari F030) - LULUS, laporan otomatis lewat USB IN
Refaktor: tambahan modul bebas-chip `src/logger_common/ina_report.{h,cpp}` (laporan INA226 + pindai I2C ke `Print&`); `src/logger_f030/main.cpp` dan `src/logger/main.cpp` (F103) sama-sama memakai `ina226`, `l3_capture`, `ina_report`. Bagian khusus F103: `plat_cycles()` = DWT->CYCCNT, `plat_hz()` = SystemCoreClock (72 MHz), keluaran USB CDC. Env `logger` memakai `+<logger_common/>`. Karena jalur OUT USB klon gagal, laporan berjalan OTOMATIS: 2 s setelah port dibuka (DTR) tercetak INA226 + rekam 5 s, diulang tiap 15 s. Build F103: Flash 40.500 B, RAM 4.996 B, bersih. (Refaktor F030 ikut berubah dan build-nya bersih, tetapi BELUM diuji di perangkat karena board logger kini F103.)
Hasil di F103 (COM18, jam 72 MHz):
- INA226: ok=1, mfg 0x5449, die 0x2260, cfg 0x4127, cal 0x0800, I2C error 0.
- Rekam 5000 ms: n=2479, polls=27560, i2c_err=0, terlambat=0, terlewat=0. Selang cuplik min 1996,2 / rata2 2017,1 / maks 2155,5 us -> **495,75 cuplikan/s**. Periode polling rata2 181 us.
- Perbandingan dengan F030 (48 MHz): n=2479 sama, 495,73/s vs 495,75/s, selang rata2 2017,1 us identik. Jadi 495,7/s adalah sifat modul INA226 ini (bukan artefak MCU atau jam logger); koreksi paper "~450/s" -> ~496/s menjadi lebih kuat.
- Selang maks di F103 sedikit lebih besar (2155 vs 2040 us): dugaan akibat interupsi USB (SOF tiap 1 ms aktif), belum dibuktikan. Nilai shunt/bus masih noise karena INA226 belum diseri dengan beban.
Masalah baru: setelah flash, `pio run -e logger -t upload` melaporkan FAILED, dan ST-Link `X` kini gagal "read version failed" (berulang, ST-Link `$` normal). Firmware baru sudah berjalan (bukti: laporan di atas), jadi flash sukses; yang gagal adalah komunikasi dengan dongle `X` setelahnya. Perlu cabut-pasang ST-Link `X` (kabel/dongle, pola mirip 13 Nov).

## L4 logger F103: input-capture tepi pin status (PA0) - KODE SELESAI & BUILD BERSIH, BELUM DIUJI DI BOARD
Catatan: bagian ini disusun 15 Nov dari kode (`src/logger/main.cpp`, `src/logger_common/edge_stats.*`, jam berkas 16:21-16:23); sesi 14 Nov tidak ditutup, jadi TIDAK ada hasil uji L4 yang tercatat. Jangan dibaca sebagai LULUS.

Rancangan:
- `TIM2` di F103 ternyata hanya **16-bit** (bukan 32-bit seperti dugaan paper/rencana L4). Di 72 MHz overflow tiap ~0,91 ms, jadi timestamp diperluas ke 64-bit dengan pencacah overflow `g_t2_ovf` (callback update HardwareTimer).
- PA0 = TIM2_CH1 menangkap tepi NAIK; CH2 dipetakan ke TI1 (CC2S=10, pin yang sama) menangkap tepi TURUN. Tanpa filter, PSC=0, ARR=0xFFFF, prioritas interupsi 0 (tertinggi).
- Penanganan race overflow vs capture (`ext_ts`): bila UIF masih terpasang dan nilai capture < 0x8000, overflow dianggap sudah terjadi (hi+1). Syarat: latensi ISR TIM2 < ~0,45 ms. Asumsi urutan callback HAL (CC1/CC2 sebelum update) belum diverifikasi di perangkat keras.
- `EdgeStats` (bebas chip): hitung tepi naik/turun, durasi HIGH/LOW/periode (min/rata2/maks), duty, frekuensi rata2, `salah_urut` (dua tepi sejenis berurutan = tepi terlewat/glitch), dan 8 tepi pertama. Dihitung di ISR tanpa pembagian; konversi ke us hanya saat cetak.
- Laporan L4 dicetak bersama L3 dalam jendela rekam 5 s yang sama (INA226 + tepi PA0 bersamaan). `g_build_id` = 0x4C4F4734 ('LOG4').
- Generator uji mandiri: PWM 100 Hz, duty 30% di PA6 (TIM3_CH1), diharapkan dijumper ke PA0. Jumper HARUS dilepas saat PA0 disambung ke pin status host.

Build (dicek ulang 15 Nov, `pio run -e logger`): bersih, Flash 46.256 B (70,6% dari 64 KB pada konfigurasi board; chip nyata 128 KiB), RAM 5.552 B (27,1%).

Belum dikerjakan / harus diuji:
- Uji mandiri jumper PA6 -> PA0: harapan HIGH 3000 us, LOW 7000 us, periode 10000 us, duty 30%, 100 Hz, salah_urut=0. Kesalahan terhadap nilai itu = bukti ketelitian capture dan penanganan overflow.
- Uji dengan pin status host sungguhan, dan pengukuran galat jam HSI host terhadap kristal logger.
- Dampak beban ISR TIM2 (2 tepi per periode uji, tetapi frekuensi nyata pin status host belum diketahui) terhadap cuplik L3 dan USB.
- Masih: akurasi INA226 vs multimeter, L5 UART1 ke host, L6 CSV + skrip PC, dongle ST-Link `X` bermasalah ("read version failed") perlu cabut-pasang sebelum flash berikutnya.
