## 2. Penjelasan kode (apa yang dilakukan tiap bagian)

### 2.1 `stop_sleep()` dan landasan NOP: `src/host/deepsleep/stop_common.h`

Fungsi ini membuat host F103 tidur Stop lalu bangun dengan benar. Urutan inti:

```cpp
rx_off();                                   // matikan penerima UART/DMA (tidak boleh ada DMA saat Stop)
USART2->CR3 &= ~USART_CR3_DMAR;
SysTick->CTRL &= ~SysTick_CTRL_ENABLE_Msk;  // SysTick akan membangunkan inti, matikan
SCB->SCR |= SCB_SCR_SLEEPDEEP_Msk;          // WFE berikutnya = tidur DALAM (Stop), bukan Sleep biasa
PB1_LO();                                   // tandai ke logger: host tidur (tepi turun)
__DSB();                                    // pastikan semua tulis register selesai sebelum tidur
asm volatile("sev; wfe; wfe; nop; nop; ... (24 NOP) ;" ::: "memory");
```

Baris penting:

- `SEV` mengangkat bendera event. `WFE` pertama langsung kembali karena bendera itu (membuang event basi). `WFE` kedua
  benar-benar tidur sampai ada event: tepi PA3 (EXTI, frame dari attacker) atau alarm RTC.
- `24 x NOP` setelah bangun: "landasan" agar instruksi pertama sesudah bangun tidak berupa instruksi 32-bit. Komentar di
  kode mencatat gejalanya: nilai register "berubah" (`add #0x1000` terbaca `#0x4000`), `ISB` dianggap instruksi tak
  dikenal, crash deterministik di frame pertama. Penyebab pastinya **belum dibuktikan**; dugaan kerja di komentar:
  instruksi 32-bit yang melintasi batas baris fetch tepat saat inti bangun. Obatnya terbukti secara empiris (K2S lulus
  59/59), bukan secara mekanisme.
- `"memory"` clobber: compiler tidak boleh memindahkan akses memori melewati blok ini.
- `const uint32_t c_w = cycles();` dibaca langsung setelah bangun. Jam inti saat itu **HSI 8 MHz** (PLL mati selama Stop),
  makanya selisih waktu dihitung dua bagian: `(c_sw - c_w) * 125` ns (siklus 8 MHz) + sisanya pada jam PLL.

Perubahan kecil lain di commit yang sama:

- Jendela pola sinkron dilebarkan (`6..11` menjadi `5..12` dan `13..22` menjadi `11..24` kali `cyc_us`). Tujuan: toleran
  terhadap jitter bangun dari Stop. Risikonya: pola palsu lebih mudah cocok; ini yang kemudian ditangani cek idle ketat.
- `dfine` bertanda: `tw - ts` dari pembacaan RTC (`CNT`/`DIV`) tidak atomik, tidur sangat singkat bisa terbaca negatif satu
  tik. Tanpa klem, `uint32_t` negatif menjadi angka raksasa. Sekarang: `dfine > 0 ? ... : 0`.

### 2.2 Cek idle ketat: `rx_idle_strict()`

```cpp
static bool rx_idle_strict() {
  if (DMA1_Channel6->CNDTR != FRAME_LEN) return false;   // DMA sudah menerima sesuatu? bukan idle
  const uint32_t t = cycles(), lim = (SystemCoreClock / 1000000UL) * 120UL;   // 120 mikrodetik dalam siklus
  while ((uint32_t)(cycles() - t) < lim) {
    if (!PA3_HIGH()) return false;                        // satu saja tepi turun = frame sedang jalan
  }
  return DMA1_Channel6->CNDTR == FRAME_LEN;
}
```

Masalah yang diselesaikan: `rx_idle()` lama hanya mengambil **satu sampel** PA3 + CNDTR. Pada 87 us pertama sebuah frame
(byte `0xA5` pada baud ~115200, 1 bit ~8,7 us, 10 bit ~87 us) pin sering sedang tinggi, jadi host salah mengira garis
diam, tidur di tengah frame, bangun di tepi acak, dan pola sinkron kadang cocok palsu. Angka 120 us dipilih lebih besar
dari run "tinggi" terpanjang di dalam frame (~9-10 bit = 87 us). Pola `(uint32_t)(cycles() - t) < lim` aman terhadap
luapan penghitung 32-bit (aritmetika modulo).

Dipakai di `stop_window.h`: `wait_event()` memanggil `rx_idle_strict()` sebelum masuk tidur.

### 2.3 Penerima dini di jalur alarm (bangun karena alarm, bukan frame)

Sebelumnya, saat bangun karena alarm RTC, host menyalakan PLL dulu (~0,3-0,5 ms) baru menyalakan penerima; frame yang
mulai di jeda itu hilang. Perbaikan: penerima dinyalakan **segera di HSI** (`g_brr_hsi`), lalu pindah ke PLL
(`pll_switch()`, `g_brr_pll`) hanya setelah garis diam ketat 120 us dan `PLLRDY`. Ada batas 8 ms (`8000UL * 8UL` siklus
@8 MHz) supaya tidak menunggu selamanya; bila garis tak pernah diam, penerima di-reset bersih (`rx_off(); rx_awake_start();`).
Konsep kuncinya: **jangan ganti baud rate di tengah byte**, karena itu merusak byte yang sedang diterima.

### 2.4 Diagnostik `DBG_RX` dan `[env:host_k2_stop_dbg]`

Makro `DBG_BAD(p)` dan variabel `g_d_*` (volatile, dibaca lewat SWD) hanya ada bila `-DDBG_RX`. Env baru

tidak berubah: tanpa flag, `DBG_BAD(p)` menjadi `((void)0)` dan tidak menghasilkan kode.

### 2.6 `run_bench.py`: toleransi frame hilang untuk varian Stop

```python
lost_ok = en["arch"].endswith("S") and en["arrived"] >= 100 and 0 < en["rx_lost"] < 0.0025 * en["arrived"]
```

Artinya: hanya arsitektur berakhiran `S` (K1S/K2S), hanya barrage (>= 100 frame tiba), dan hilang harus
**kurang dari 0,25 %**. Contoh: 600 frame tiba -> batas 1,5 -> hanya **1 frame hilang** yang masih lolos; 2 gugur. Itu
sesuai tabel logbook (blok 1 dan 4 menggugurkan run dengan "hilang >= 2"). Frame **rusak** (`rx_bad`) tetap tidak
ditoleransi. Nilai yang ditoleransi tetap dicatat di `rx_lost_toleransi` supaya tidak disembunyikan.

Juga: `ELF` dan `KELOMPOK` diperluas ke K1S..K4S; `flash_host()` untuk varian Stop memakai `tools/flash_stop.py`
(SWD hanya hidup saat inti terjaga, jadi harus "ditangkap" dulu).

### 2.7 `tools/uji_galat_stop.py`: uji jalur galat

Skrip menjalankan jendela 60 s sambil mengirim gangguan ke attacker pada detik tertentu:

- `rencana = [(detik_sejak_START, aksi)]` dijalankan di **thread** terpisah (`peristiwa`) yang mulai ketika baris
  `>START` dari host terlihat (`on_line`). Jadi waktu gangguan relatif terhadap awal jendela, bukan jam dinding.
- `G3` memakai `sum([[...] for i in range(10)], [])` untuk meratakan daftar bersarang: hidup/mati tiap 1,5 s.
- Kriteria lulus khusus galat: jendela utuh (selisih < 0,6 s dari 60), `S_cpu` logger vs host < 0,5 poin, rusak = 0,
  ada permintaan terlayani, bangun palsu <= 20. Sesudah tiap gangguan ada **run pemulihan A** sebagai bukti host tidak
  terkunci.

### 2.8 `tools/pulihkan_host.py`

Host bisa "terkunci" karena firmware mematikan SWD saat tidur (percobaan "matikan SWJ selama tidur" mengunci chip).
Pemulihan: `BOOT0 = 1` + POR sehingga chip menjalankan bootloader sistem (SWD hidup di sana), lalu OpenOCD:
`halt` -> `stm32f1x mass_erase 0` -> `program ... verify` -> `shutdown`. `reset_config none` karena tidak ada garis reset
terhubung.

### 2.9 `tools/kalibrasi_shunt.py`: regresi melalui titik nol

Ide: INA226 membaca tegangan shunt dalam satuan 2,5 uV. Arus = `(mentah - offset) x 2,5e-6 / R x 1000` (mA). Kalibrasi
mencari R efektif:

```python
x = [mentah - offset]                      # satuan bersih
k = sum(x*y) / sum(x*x)                    # kemiringan kuadrat-terkecil, garis dipaksa melalui nol
r_eff = LSB_V * 1000.0 / k                 # dari y = k x  dan  y = x*LSB*1000/R
```

Ada juga regresi bebas (kemiringan + intersep) **hanya sebagai pemeriksaan**: bila intersep `c` besar (> 5 % dari arus
maksimum), skrip memperingatkan bahwa titik nol atau linearitasnya bermasalah. Ketidakpastian akhir:
`u_kal = sqrt(u_ref^2 + u_fit^2)`; menggantikan asumsi 5 % sementara dengan angka hasil ukur. Skrip menutup dengan
mencetak perintah `analisis_d.py --rshunt ... --offset ...` siap salin.

## 4. Konsep yang perlu dikuasai

1. **Mode daya Cortex-M3/STM32F1**: Sleep (CPU berhenti, jam hidup) vs **Stop** (jam inti mati, regulator bisa
   low-power; SRAM dan register dipertahankan) vs Standby (RAM hilang). Stop dipilih karena RAM dan keadaan program
   tetap ada. Setelah Stop, jam sistem kembali ke **HSI 8 MHz** dan PLL harus dinyalakan ulang.
2. **WFI vs WFE vs SEV**: WFI menunggu interupsi; WFE menunggu *event* (termasuk event EXTI tanpa ISR). Register event
   1-bit: SEV mengisinya, WFE pertama mengosongkannya dan kembali segera. Itu alasan pola `SEV; WFE; WFE`.
3. **`SLEEPDEEP` + `PWR_CR.LPDS`**: bit di `SCB->SCR` yang membuat WFI/WFE masuk tidur dalam; LPDS memilih regulator
   low-power di Stop.
4. **RTC sebagai sumber bangun**: LSE 32,768 kHz; di kode ini 1024 tik per detik (`secs * 1024`). Pembacaan counter
   multi-register (CNT dan DIV) tidak atomik sehingga perlu penanganan bacaan -1.
5. **Pipeline fetch / prefetch dan instruksi Thumb-2 32-bit vs 16-bit**: dasar dugaan di balik landasan NOP.
   Pelajari bagaimana instruksi 32-bit dapat melintasi batas fetch dan mengapa NOP 16-bit "menyelaraskan" ulang.
6. **UART dan baud rate**: BRR = fPCLK / baud. Frame 10 bit (start + 8 data + stop). Mengubah BRR di tengah byte
   merusaknya. Galat baud < 1 % dari pembagi bulat pada PCLK 8 MHz vs 48 MHz.
7. **DMA + CNDTR**: `CNDTR == FRAME_LEN` berarti belum ada byte masuk ke DMA; bagian dari definisi "idle".
8. **1-Wire dan overdrive (DS28E38)**: slot waktu bit-bang dengan DWT `CYCCNT`; overdrive memangkas waktu slot ~8x.
   Tunggu tetap (130 ms) diganti polling sehingga total turun 192,5 -> 115,6 ms per tanda tangan.
9. **ECDSA (P-256) secara ringkas**: tanda tangan = pasangan (r, s) dari nonce acak k dan kunci privat; DS28E38
   menghitungnya di perangkat keras, K1 melakukannya di perangkat lunak (Mbed TLS) sehingga latensi 654,9 ms vs 116,2 ms.
10. **Metrologi**: kalibrasi, offset, ketidakpastian gabungan `sqrt(a^2 + b^2)`, regresi kuadrat-terkecil melalui nol
    vs bebas, dan alasan pengukuran harus *tanpa debugger*.
11. **Validitas data**: kriteria sah/gugur ditetapkan sebelum melihat hasil; toleransi yang dilonggarkan harus dicatat
    dan dilaporkan, bukan disembunyikan.
12. **Reproduktibilitas**: provenance (SHA-256 + git HEAD + dirty) dan gerbang biner identik.

Kata kunci pencarian: "STM32F1 Stop mode WFE SEV", "Cortex-M3 instruction fetch buffer wake from sleep", "STM32 RTC
alarm wake up from Stop", "INA226 shunt calibration offset", "regression through the origin", "DS28E38 overdrive".

## 5. Latihan (dengan jawaban)

**Soal 1.** Mengapa `stop_sleep()` memakai `SEV; WFE; WFE` dan bukan satu `WFE`?
**Jawab.** `WFE` mengecek register event. Bila ada event basi (mis. dari EXTI/alarm sebelumnya), `WFE` pertama kembali
langsung tanpa tidur. `SEV` sengaja mengisi register itu agar `WFE` pertama yang menghabiskannya; `WFE` kedua tidur
sungguhan.

**Soal 2.** `rx_idle()` lama memeriksa PA3 sekali. Tunjukkan dengan angka mengapa itu bisa salah, dan mengapa 120 us dipilih.
**Jawab.** Pada baud ~115200 satu bit ~8,7 us. Run tinggi
terpanjang di dalam frame ~9-10 bit ~ 87 us (angka dari komentar kode; byte data/checksum bisa berisi banyak bit 1 berturutan). Sampel tunggal bisa jatuh di salah satu run tinggi itu sehingga garis
"tampak diam". Bila PA3 diwajibkan tinggi terus lebih lama dari run tinggi terpanjang (87 us), maka 120 us (> 87 us dengan
margin) memastikan tak ada frame sedang berlangsung.

**Soal 3.** Run barrage K2S tiba 600 frame. Berapa maksimum frame hilang agar run tetap sah, dan apa yang terjadi bila
2 frame hilang? Bagaimana dengan 1 frame rusak?
**Jawab.** Syarat `0 < rx_lost < 0,0025 x 600 = 1,5` -> hanya 1 frame hilang yang diterima (dicatat di
`rx_lost_toleransi`). 2 hilang -> run gugur (cocok dengan "hilang >= 2" di logbook). 1 frame rusak -> gugur, karena
`rx_bad` tidak mendapat toleransi.

**Soal 4.** Dalam `kalibrasi_shunt.py` diperoleh `k = 0,0300 mA/satuan`. Berapa `R_eff`? (LSB = 2,5e-6 V)
**Jawab.** `R_eff = LSB x 1000 / k = 2,5e-6 x 1000 / 0,0300 = 0,0833 ohm` (sesuai dengan dugaan shunt ~0,08 ohm
di memori proyek). Faktor koreksi arus terhadap nominal 0,100 ohm = 0,100/0,0833 ~ 1,2 kali.

**Soal 5.** Mengapa `provenance.json` tidak ditanam ke dalam `firmware.bin`, dan apa gunanya `.json.tmp` lalu `replace()`?
**Jawab.** Gerbang `cek_biner.py` menuntut biner identik bit-demi-bit; hash atau commit di dalam firmware mengubah biner
sehingga gerbang selalu gagal (dan hash komitnya bergantung pada kode itu sendiri, sirkular). Tulis-sementara lalu ganti
nama membuat pergantian berkas atomik: pembaca tidak akan pernah melihat JSON setengah jadi, termasuk bila proses
terhenti di tengah penulisan.

**Soal 6 (analisis).** Hasil K2S barrage: tingkat layanan 85,5 %, K1S barrage 15 %. Mengapa K2S melayani jauh lebih
banyak, dan mengapa angka hematnya K2 (80 %) tidak boleh ditulis sebagai "efek Stop saja"?
**Jawab.** Latensi K2S 116,2 ms vs K1S 654,9 ms; pada beban penuh jumlah permintaan yang bisa diselesaikan per jendela
sebanding dengan 1/latensi. Hemat K2 mencampur dua perubahan: Stop menggantikan WFI **dan** overdrive+polling
menggantikan kecepatan standar+tunggu tetap (~192 ms -> ~116 ms). Data tidak memisahkan keduanya, sehingga hanya K1 (yang
hanya terkena Stop) yang bisa dilaporkan sebagai efek Stop murni.
