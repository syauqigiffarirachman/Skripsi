## 2. Penjelasan kode

### 2.1 Attacker: mode C (`src/attacker/main.cpp`)

**Tujuan:** sampai kemarin attacker hanya punya dua laju tetap (A = 1/s, B = 10/s). Skenario C butuh periode
sembarang (mis. 654,1 ms), jadi ditambah perintah konsol `p<periode_us>` + Enter.

1. `enum Mode` ditambah `MODE_C = 3`. Jalur A/B tidak disentuh (komentar di `modeStartPeriod`: “dibuat terpisah dari
   `modeStart()` agar jalur mode A/B tidak berubah sama sekali”).
2. Konstanta batas: `PERIOD_MIN_US = 1000` (1 ms) dan `PERIOD_MAX_US = 10 000 000` (10 s). Batas bawah masuk akal
   karena satu frame 36 B pada 115200 baud 8N1 butuh 36 × 10 / 115200 ≈ **3,1 ms**; periode < 3,1 ms membuat frame
   bertumpuk di UART.
3. `timerStartUs(periodUs)`: `Ticker.setOverflow(periodUs, MICROSEC_FORMAT)` — pustaka STM32duino menghitung sendiri
   prescaler dan nilai ARR TIM3 (16-bit) dari periode dalam µs. Urutan `pause → setOverflow → attachInterrupt →
   refresh → resume` sama dengan `timerStart()` lama. `refresh()` memicu update event palsu → itulah gunanya
   `g_skipFirstTick = true` (tick pertama dibuang, lihat komentar lama di bagian atas file).
4. `modeStartPeriod()` mereset `g_seq`, `g_tickCount`, `g_sendFlag`, mencatat `g_startMillis`, lalu menjalankan timer.
5. **Parser `p<angka>` di `loop()`** — sebuah mesin keadaan kecil dengan flag `g_pEntry`:
   - `'p'` → `g_pEntry = true`, nilai dan jumlah digit direset.
   - Selama `g_pEntry`: digit `0–9` menambah `g_pVal = g_pVal*10 + digit` (maksimum 8 digit, cukup untuk 10 000 000),
     lalu `return` (karakter sudah dipakai, tidak diteruskan ke `switch`).
   - `\r`/`\n` → `periodEntryFinish()`: bila ≥ 1 digit dan nilai dalam [1000; 10 000 000] → `modeStartPeriod`, selain itu
     cetak “periode ditolak” **tanpa mengubah mode** yang sedang jalan.
   - Karakter lain → batalkan entri, cetak “dibatalkan”, lalu karakter itu **tetap diproses** `switch` (jadi `px`
     membatalkan lalu menghentikan, bukan menelan `x`).
6. `printStatus()` untuk mode C menambahkan `periode_us=` supaya `run_bench.py` bisa memeriksa `berjalan=ya` dan
   manusia bisa memeriksa periode.

Yang perlu diperhatikan saat membaca: `return` di tengah `loop()` aman karena `g_sendFlag` diperiksa **di awal** `loop()`
pada iterasi berikutnya (tertunda ≤ satu iterasi, mikrodetik). Pengiriman frame sendiri **bukan** di ISR, melainkan di
`loop()` — ISR hanya menaikkan `g_sendFlag`.

### 2.2 `tools/1_akuisisi/periode_kapasitas.py`

Mengubah hasil uji pendahuluan (5 run A + 2 run B per arsitektur, tanpa IDLE) menjadi periode yang dikirim:

- `t_sign` = rerata `lat_mean_ms_nyata` run A sah **ditimbang** `lat_n` (jumlah tanda tangan per run) → rerata atas
  seluruh ±295 tanda tangan, bukan rerata dari rerata.
- `lambda_B` = Σ`N_dtg` / Σ`T_obs_log_s` pada run B sah: laju attacker yang **sebenarnya** menurut kristal logger
  (nominal 10/s). Pada K1S ternyata 10,0152/s → jam HSI attacker sedikit cepat.
- `k = 10 / lambda_B` (K1S: 0,99848). `periode_kirim_us = round(t_sign / k)` → 654 100 / 0,99848 ≈ 655 095 µs.
  Dengan perintah itu, periode **nyata** (kristal logger) = t_sign.
- Bila tidak ada run A sah atau run B sah → `ValueError`; tidak ada `k = 1` diam-diam (anti-sasaran di desain: “laju C
  bukan ρ ≈ 1 tetapi tidak ketahuan”).

> Catatan docstring: “k > 1: jam HSI attacker lambat”. Sebaliknya, k < 1 (hasil hari ini) = attacker cepat, perintah
> harus diperpanjang.

### 2.3 `tools/1_akuisisi/run_bench.py`

- `SCEN["C"] = (4, "PERIODE")` — “4” sama dengan A/B (perintah logger lewat baud); `"PERIODE"` adalah penanda bahwa
  perintah attacker bergantung arsitektur.
- `perintah_attacker(scen, arch, periode)` — satu fungsi kecil, mudah dites: A → `"a"`, B → `"b"`, IDLE → `None`,
  C → `"p<us>\n"` dari JSON; periode tak ada → `SystemExit` (sesi berhenti, tidak memakai laju lain).
- `tambah_kapasitas()` — kolom baru per run C: `periode_us` (periode nyata yang dituju) dan
  `rho_nyata = lambda_eff_rps × t_sign_ms / 1000`. Jadi ρ yang **diukur**, bukan yang diniatkan, ikut dilaporkan.
- `idle_luar()` + parameter `idle_luar` pada `energi_sesi()` — sesi C tidak punya run IDLE (keputusan peneliti), maka
  `P_idle` diambil dari IDLE `stop_final`. Kunci dinormalkan (`K1` → `K1S`). IDLE sesi **selalu menang** bila ada; sumbernya
  dicatat di kolom `P_idle_sumber` (`sesi` / `stop_final`).
- `TOL_HILANG = {"C": 0.01}`, bawaan 0,0025: toleransi frame hilang naik dari 0,25 % ke 1 % untuk C (lihat bagian 3).
  `analyse(..., scen=None)` menerima nama skenario hanya untuk memilih ambang ini.
- `KELOMPOK` ditambah `("K1S","C") → "K5S"` dan `("K2S","C") → "K6S"`; `METRIK` ditambah `rho_nyata`.
- Opsi CLI baru: `--periode` (berkas JSON) dan `--idle-dari` (runs.csv pengganti IDLE). Sebelum run pertama, perintah
  `plan` mengecek **semua** arsitektur skenario C punya periode (gagal lebih awal, bukan di tengah sesi 40 menit).

### 2.4 `tools/3_analisis/analisis_kapasitas.py`

## 3. Mengapa begitu

| Keputusan | Alasan | Alternatif yang ditolak | Risiko |
|---|---|---|---|
| ρ = 1 lewat **periode tetap = t̄_sign** (pendekatan 1) | Firmware host tidak berubah → data tetap sebanding dengan 120 run lama; cukup ubah attacker | Loop tertutup (host memberi sinyal “selesai”): paling harfiah, tapi butuh pin baru + firmware host baru; PB1 tak bisa dipakai di K2 karena CPU tidur Stop di tengah tanda tangan. Sapuan laju 0,8–1,2×: run terlalu banyak, N per titik < 30 | Latensi bergetar (K2 ±115–121 ms), jadi ρ nyata sedikit ≠ 1 → ditangani dengan melaporkan `rho_nyata` per run |
| Pakai **rata-rata**, bukan maksimum | Θmax = 1/t̄_sign adalah definisi kapasitas di Bab 3 | Maksimum → ρ < 1 selalu | – |
| Kalibrasi jam attacker lewat run B | HSI F030 sekitar ±1 %; galat 1 % pada ρ = 1 sudah menggeser beban 1 % ke sisi mana pun. 2 run B ≈ 1200 frame → resolusi ±0,2 % | Osiloskop/logic analyzer (alat tambahan, belum ada) | Kalibrasi diambil pada suhu/saat tertentu; HSI berubah dengan suhu |
| Mode C **ditambah di samping** A/B | Anti-sasaran: perilaku A/B tak boleh berubah supaya data 18 Nov sah | Menggeneralisasi `modeStart` ke periode bebas (lebih rapi, tapi menyentuh jalur A/B) | Duplikasi kecil; dijaga dengan uji ulang A/B (N_dtg per 60 s sama) |
| `IDLE` dipakai ulang dari `stop_final` | Keputusan peneliti: papan sama, kabel hanya ditata ulang; IDLE K2S 27 Nov (2,43 mA) vs lama (2,45 mA) selisih ±0,02 mA | Ambil IDLE baru (butuh run tambahan di tiap sesi) | Pergeseran kondisi ukur; karena itu metrik P_dyn/E_lyn diposisikan sekunder, utama = besaran mutlak |
| Toleransi frame hilang C = 1 % | Periode serangan ≈ siklus host, sehingga fase frame bergeser pelan dan berulang kali jatuh di celah pulih-dari-Stop K2S (1–4 frame/run) | Tetap 0,25 % → banyak run gugur (dua run gugur sudah terjadi, dibuat blok 3b) | Longgar: harus **dilaporkan sebagai temuan**, bukan disembunyikan; frame **rusak** tetap harus 0 |
| Pola ABBA (K1S | K2S | K2S | K1S) | Meniru Bab 3: drift (suhu, tegangan USB) terbagi rata antar arsitektur; flash hanya dua kali | Blok acak penuh | Blok 4 belum masuk manifes |
| Perintah periode di `run_bench.py` dikirim sebagai `p<us>\n` dan gagal keras bila tak ada | Menghindari run C memakai laju salah secara diam-diam | Nilai bawaan | – |

Konsep embedded yang menempel di keputusan ini:

- **Timer 16-bit & prescaler.** TIM3 menghitung sampai ARR ≤ 65 535. Untuk 654 ms pada 48 MHz, `setOverflow` memilih
  prescaler sekitar 480–500 sehingga satu tick ≈ 10 µs → resolusi sekitar 0,002 % dari periode (jauh di bawah galat HSI).
- **HSI vs kristal.** Attacker memakai osilator internal RC (±1 %), logger memakai kristal (jauh lebih akurat). Karena
  itu waktu “nyata” selalu diukur dari log logger, dan perintah dikoreksi dengan k.
- **Stop mode host.** K2S tidur Stop saat menunggu DS28E38; frame yang tiba tepat saat CPU baru bangun/pulih bisa
  terlewat (UART tidak aktif). Ini penyebab frame hilang 1–4 per run pada C.
- **ρ = λ · t_sign** (utilisasi antrean M/D/1 yang disederhanakan). ρ < 1 antrean stabil; ρ > 1 antrean tumbuh dan
  host menyimpan hanya satu permintaan tertunda, sisanya terlewat (`stop_window.h`). Pada ρ = 1 tepat, sedikit saja
  pergeseran memutuskan apakah ada permintaan terlewat — itulah mengapa ρ_nyata dilaporkan per run.

## 4. Konsep yang perlu dikuasai

1. **Utilisasi dan kapasitas.** Θmax = 1/t_sign; ρ = λ/Θmax. A: K1S ρ ≈ 0,65 (1 × 0,654), K2S ρ ≈ 0,12;
   B: K1S ρ ≈ 6,5, K2S ρ ≈ 1,16 (angka di desain memakai t_sign 18 Nov: 654,9 / 116,2 ms). C memaksa ρ = 1 untuk keduanya,
   sehingga **beban relatif sama** dan yang dibandingkan murni arsitektur.
2. **Kalibrasi pengukuran dengan pengukuran lain.** Laju attacker tidak dipercaya dari nilai nominal, tetapi diukur
   (Σ frame / Σ waktu logger) lalu dipakai sebagai faktor koreksi k. Prinsip sama: kalibrasi R_shunt INA226 21 Nov.
3. **Rerata berbobot.** Rerata latensi seluruh tanda tangan = Σ(mean_run × n_run)/Σ n_run, bukan rerata dari rerata.
4. **Uji hipotesis banyak metrik.** Welch (tidak mengasumsikan variansi sama), Mann–Whitney sebagai cek non-parametrik,
   Holm mengendalikan peluang kesalahan tipe I untuk keluarga uji (6 metrik × 3 pasangan = 18 uji).
5. **Bootstrap persentil.** Resampel dengan pengembalian 10 000 kali, hitung selisih rerata tiap kali, ambil persentil
   2,5 dan 97,5 → IK 95 % tanpa asumsi distribusi.
6. **Desain eksperimen ABBA.** Menyeimbangkan drift waktu; tiap arsitektur diukur di awal dan akhir.
7. **Tes tanpa perangkat keras.** Log sintetis + fungsi murni (`perintah_attacker`, `hitung_periode`) → logika bisa
   dites di PC; hanya akuisisi yang butuh papan.

Cari lebih jauh: “STM32 HardwareTimer setOverflow MICROSEC_FORMAT”, “Holm–Bonferroni vs Bonferroni”, “percentile
bootstrap confidence interval”, “utilization factor queueing ρ = λ/μ”.

## 5. Latihan

1. Attacker K2S dikalibrasi: λ_B = 10,00291/s dan t_sign = 116,1544 ms. Hitung k dan periode kirim yang benar.
   Jelaskan arah koreksinya (jam attacker cepat atau lambat?).
2. Mengapa `periode_kirim_us` memakai `t_sign / k` dan bukan `t_sign × k`? Uji dengan K1S (k = 0,99848).
3. Parser `p<angka>`: apa yang terjadi bila Anda mengetik `p1234x` + Enter? Dan `p5` + Enter? Dan `p123456789` (9 digit)?
4. Run C K2S menghasilkan 515 frame tiba dan 4 hilang, 0 rusak. Sahkah menurut aturan C? Dan menurut aturan B? Bagaimana
   bila 1 hilang + 1 rusak?
5. Mengapa metrik utama dipilih `I_avg`, `P_avg`, `S_cpu`, `TL`, latensi, bukan `E_lyn` / `P_dyn`? Apa risikonya jika
   P_idle `stop_final` berbeda 0,1 mA dari kondisi hari ini?
6. (Konsep) Pada ρ = 1 tepat, mengapa frame hilang bisa tetap terjadi walaupun “rata-rata” kapasitas cukup? Hubungkan
   dengan getaran latensi K2 (±115–121 ms) dan batas satu permintaan tertunda.

### Jawaban

1. k = 10 / 10,00291 = **0,999709**; periode kirim = 116 154,4 µs / 0,999709 ≈ **116 188 µs** (sama dengan JSON).
   λ_B > 10 → attacker mengirim lebih sering dari perintah → jam **cepat** → perintah harus **diperpanjang**.
2. Periode nyata = periode kirim × k (karena attacker mengirim 1/k kali lebih cepat dari yang diminta). Agar nyata =
   t_sign, kirim = t_sign / k. K1S: 654 100 / 0,99848 ≈ 655 095 µs. Memakai `× k` akan memperparah galat (≈ 653 106 µs →
   nyata ≈ 652 100 µs, galat ~0,3 %).
3. `p1234x`: digit terkumpul, `x` bukan digit/Enter → cetak “periode dibatalkan”, entri dibuang, lalu `x` diproses
   `switch` → **mode dihentikan** (modeStop). `p5` + Enter: 5 < 1000 → “periode ditolak (1000..10000000 us)”, mode
   sebelumnya tak berubah. `p123456789`: digit ke-9 tidak diterima (`g_pDigits < 8` gagal), jatuh ke “batalkan”, lalu digit
   `9` diteruskan ke `switch` → `default: printHelp()`; entri batal.
4. C: 4/515 = 0,78 % < 1 % dan rusak 0 → **sah** (dicatat `rx_lost_toleransi=4`). B: 0,78 % > 0,25 % → **gugur**.
   1 hilang + 1 rusak: frame rusak tidak ditoleransi → **gugur** di semua skenario.
5. P_dyn = P_avg − P_idle, jadi galat P_idle masuk langsung. Selisih 0,1 mA × ~3,3 V ≈ 0,33 mW bias sistematis pada
   P_dyn untuk semua run C — bisa berarti sebanding dengan perbedaan antar arsitektur pada K2S. Besaran mutlak tidak
   terkena bias itu. Itu sebabnya I_tidur run C dipantau: bila bergeser > 0,1 mA dari 2,45 mA, dilaporkan.
6. Hanya satu permintaan boleh tertunda. Jika satu tanda tangan memakan 121 ms padahal periode 116 ms, permintaan
   berikutnya menunggu (1 tertunda); tanda tangan yang lebih cepat tidak “menabung” kapasitas. Fase frame juga bergeser
   pelan terhadap siklus host (periode ≈ siklus) sehingga sesekali jatuh di celah pulih-dari-Stop. Rata-rata cukup
   tidak menjamin tiap permintaan terlayani — itu inti ρ = 1 sebagai titik kritis.
